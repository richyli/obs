Claude-Mem

https://hackmd.io/@BASHCAT/S1tqslOwWe?utm_source=preview-mode&utm_medium=rec https://github.com/thedotmack/claude-mem

最近出的Claude-Mem算是解決了Claude Code長期以來的一個明顯短板。

很多人在使用 Claude Code 時都會遇到同樣的問題：沒有跨對話的持久記憶。每次重開 session，都必須重新說明專案背景、架構與需求，不只消耗 token，也打斷工作節奏。

這個專案做的事情很單純但很關鍵，把過去對話與操作內容自動整理、壓縮，再在未來對話中只注入「真正相關的上下文」，而不是全部塞回去。

它的做法包含幾個核心機制：

• 自動捕捉使用過程中的內容

• 透過 AI 進行記憶壓縮

• 只在需要時載入關鍵上下文

• 分層式提取資訊，而不是一次讀取所有資料

官方提到，這樣可以顯著降低每次對話所需的 token 數量，最多可將每次對話所需的 token 減少 95%，同時讓工具呼叫次數變得更有效率。

安裝方式也很簡單，兩個指令就能啟用，重啟之後就能開始使用持久記憶。

目前 GitHub 星數已飆升29.9k，如果你長期在用 Claude Code 開發專案，這類「記憶層」工具很值得關注。它不只是省 token，而是試圖為 AI 工作流建立一層更穩定的長期上下文管理機制。

一行指令，秒開「Yes-All」模式

最簡單暴力的做法，就是在任何 claude 指令後面加上：

claude --yes --skip-confirm

  • --yes：對所有「y/n」問題自動回答 yes
  • --skip-confirm：跳過任何需要人類二次確認的步驟

把這行寫進你的 Makefile 或 package.json script，之後只要 npm run claude 就能全自動跑。

永久設定：讓 .claude.json 幫你記住

不想每次打參數？在專案根目錄放一個 .claude.json，貼上：

{ "autoYes": true, "skipConfirm": true, "silent": false }

存檔後，無論誰跑 claude 都會自動 yes。
（小提醒：把 .claude.json 加進 .gitignore，避免隊友被強迫自動化。）

環境變數也行：CI/CD 最愛

GitHub Actions、GitLab CI 或任何容器環境，只要在 env 區塊加：

CLAUDE_AUTO_YES: 1 CLAUDE_SKIP_CONFIRM: 1

這樣就算在無互動的容器裡，Claude Code 也能乖乖閉嘴執行。

常見坑位速查表

情境 指令範例 備註
本地測試 claude --yes --skip-confirm 先跑一次看看會不會刪錯檔
CI 環境 claude --yes --skip-confirm --silent --silent 可關閉進度條，減少 log 噪音
多人協作 .claude.json 加 .gitignore 避免隊友被迫自動 yes
安全顧慮 加 --dry-run 先預覽 確認沒問題再去掉 --dry-run

進階：只在特定步驟自動 yes

有時你想讓 Claude Code 自動重構，但部署前還是想親眼看一眼。這時可用「分階段指令」：

# 自動重構 claude refactor --yes --skip-confirm # 部署前再問我 claude deploy

結語：把「提問」留給人類，把「執行」交給 Claude Code

設定好 --yes 與 .claude.json 後，你就能把重複性工作完全託管給 Claude Code。記得先在測試專案跑一次，確認它不會把整個 repo 刪光，再正式上線。自動化不是偷懶，而是把大腦留給更有創意的事。

Subagent DAG：何時要把 skill 拆成多個 subagent

Claude Code 的 Agent 工具會在獨立 context 中跑一個子代理，跑完只回傳摘要到主對話。多個無依賴的 step 可在同一則訊息內發多個 Agent call，runtime 會真正並行執行。把 pipeline-style 的 skill（如 /daily、/weekly）改寫成 subagent DAG，等於是把「一段長腳本」變成「一張有節點和邊的執行圖」。

好處
  1. 保護主對話 context：每個 skill 動輒掃 wiki/ 數百檔，直接在主對話跑會在第 2–3 步就把 context 塞滿，導致後段步驟品質下降或被迫壓縮。subagent 在隔離 context 跑完只回摘要，主對話 context 增長從「O(處理檔案數)」變成「O(step 數)」。
  2. 真並行加速：同一 message 內多個 Agent call 並行執行。/daily 的 summary-note 與 random-link 互不依賴，並行可省一半時間。
  3. 失敗隔離：某個 subagent 失敗不會污染主對話狀態，記錄錯誤後可直接跳下一步。
  4. DAG 顯式化：把依賴關係寫成圖，比「依序執行步驟 1–10」更容易看出哪裡可並行、哪裡會卡。
  5. prompt 可審查：每個 step 的 prompt 被寫進 skill 檔，比散落在主對話的隱含指令更易維護。
何時該這樣做

✅ 適合改成 subagent DAG：

  • Pipeline-style skill：多個步驟串接、每步處理大量檔案（/daily、/weekly、/audit+索引刷新等）
  • 步驟之間有可並行的區塊（兩個以上 step 互不依賴）
  • 單一 skill 的 context 預估超過 100K tokens（掃全 wiki、批次處理論文等）
  • 需要 fan-out：對 N 個目標各跑同樣處理（例如對 N 篇論文各做 paper-image 抽圖）

❌ 不適合：

  • 互動式 skill：需要使用者中途回答的（/today、/workplan、/diary）—— subagent 跑完才回主對話，無法中途問你
  • 短任務：總共只動 1–3 個檔案的 skill，包 subagent 反而增加 overhead
  • 強順序依賴：每步都需要前步的完整輸出而非摘要（subagent 摘要可能丟資訊）
  • 需要看完整中間產出：debug 或第一次跑某 pipeline 時，主對話應該看到細節而非摘要
設計原則
  • subagent_type 選擇：要寫檔的用 general-purpose；純查詢用 Explore（read-only，更快）
  • prompt 強制回傳摘要：明寫「回報：N 個處理檔、檔名列表、異常」，禁止 subagent 貼出完整內容
  • 並行區塊在同一 message：兩個無依賴的 Agent call 必須寫在同一則回應內，否則退化為順序
  • 跨 step 資料傳遞：主對話收摘要 → 組成 struct → 塞進下游 step 的 prompt（不要讓下游 subagent 重新掃檔還原狀態）
  • session 檔機制：對依賴鏈長的 pipeline，第一個 step 寫 wiki/_session/current_run.md 鎖定本輪範圍，後續 subagent 讀此檔避免重複掃描
  • 失敗處理：subagent 失敗 → 該 step 摘要填「失敗：<簡述>」→ 繼續下一步，不回頭重試
反模式：不是「另一個對話框」

Claude Code 的 Agent 是 subagent 在獨立 context 跑，不是真的開新 terminal/窗口。如果想要真正多窗口並行（例如同時跑 /jp-daily 和 /news-sec），那是 /schedule 或手動多開 Claude Code instance 的事，不是 Agent 工具。對有 DAG 依賴的 pipeline，跨窗口執行反而會破壞順序保證（沒辦法 enforce 步驟 6 等步驟 1–5），所以這類場景只該用 subagent。

範例：/daily 的 DAG
1 read-citavi
  └─ 1.5 journal-watch (gate)
       └─ 1.6 weekly (gate)
            └─ 2 extend
                 └─ 3 methodology
                      └─ [4 summary-note] ‖ [5 random-link]   ← 同一 message 並行
                           └─ 6 book-edit
                                └─ 7 scholar → 8 audit → 9 daily_report → 10 wish-list

完整實作見 .claude/commands/daily.md。

反例：/today 為何不該整體 subagent 化

不是所有 pipeline-style skill 都該改 subagent DAG。/today 是好的反例。

表面像 pipeline，本質是互動式 dashboard

/today 有 14 個步驟（負一、零、零·二、零·二·五、零·三、零·五、一~八），看起來和 /daily 類似。但拆開看：

類型 步驟 能否 subagent 化
MCP 呼叫 / Python 腳本 stdout 負一、零·二、零·二·五、七·六 ❌ 沒必要，本來就輕量
互動式（等使用者回覆） 七、七·五、八 ❌ subagent 跑完才回主對話，無法中途問你
要展示給使用者看的內容 零·五（昨日日記）、三~六（dashboard、警示） ❌ subagent 只回摘要會丟掉展示細節
重 context 的子 skill 呼叫 零（jp-daily）、零·三（news-sec） ✅ 這兩個值得改
三條判斷規則

從這次經驗萃取：

  1. 看互動需求：skill 內若有「等使用者回覆 done X / dl Y / 選項」的 step，整體不能 subagent 化——subagent 跑完才回主對話。
  2. 看輸出用途：subagent 只回摘要。若 step 的輸出是「直接展示給使用者讀的儀表板/日記/警示」，subagent 化會丟掉關鍵展示細節；若是「寫到檔案、主對話不用看完整內容」，才適合 subagent。
  3. 看 context 重量：主要由 Python 腳本（today_run.py、weather_brief.py、sleep_advisor.py）處理重活的 step，主對話只接收 stdout，沒有 context 稀釋問題，不需要 subagent。
選擇性 subagent：對「重 context 的子 skill 呼叫」做手術

/today 內唯二值得改的是 /jp-daily（抓 Yahoo News + 改寫教材）和 /news-sec（抓 60 則全球新聞 + 4000 字 brief）。這兩個 step 符合三條件：

  • 完全沒互動需求（自動執行）
  • 輸出寫到檔案（learn/jp/、learn/news/），主對話不需要看內容
  • 子 skill context 量大（抓網頁、寫長文）

改寫成 Agent call + 強制摘要回報後，主對話只記「檔路徑 + 條數 + 字數」一行，不會被 Yahoo News 原文或 4000 字 brief 灌爆。

一般原則：subagent 是 手術刀，不是 斧頭

看到「多步驟 skill」不要反射性想全部包 subagent。先標每個 step 屬性：

  • 互動 / 自動？
  • 輸出是給人看 / 寫進檔案？
  • context 重 / 輕？

只對「自動 + 寫檔 + 重 context」的 step 動刀。/daily 之所以整體適合 subagent DAG，是因為它所有 step 都符合這三個條件（全自動、產出寫進 wiki/、每步動數百檔）。/today 不是。
