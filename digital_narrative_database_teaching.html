digital narrative database teaching

純前端的數位敘事（digital narrative teaching 25）讓資料一次性嵌入頁面、用滾動或互動呈現。有後端資料庫的數位敘事則允許：

  • 讀者寫入 — 每位讀者的輸入成為下一位讀者看到的內容
  • 持續累積 — 事件、案例、提報隨時間增長
  • 個人化記憶 — 系統記住你的歷史
  • 群眾協作 — 多位記者 / 志工 / 編輯共同建構同一資料庫
  • 即時更新 — 後端推送的新事件自動刷新前端

本講義教學生如何辨識題目是否適合資料庫、選擇對應的 Firestore 資料結構，並在 Firebase 上做出 5 個漸進難度的練習。

一、五個訊號：你的題目需要資料庫

當題目至少符合以下其一，純前端不夠用，要考慮後端資料庫：

訊號 描述 對應例子
訊號 1：你的故事 + 我的故事 = 我們的故事 每位讀者的輸入或經驗，透過聚合成為更大的故事 DN You Draw It NYT、DN Lost Mothers ProPublica
訊號 2：事件持續發生 故事還沒結束，後續會持續加入新案例 DN Documenting Hate ProPublica、DN Mass Killing Database USA Today、DN Trial and Terror Intercept
訊號 3：每個人想看自己的位置 讀者要查「我家附近怎樣」「我這群人怎樣」 DN ToxMap ProPublica、DN Opportunity in Cities NYT、DN Dollars to Megabits Markup
訊號 4：比較我與群體 讀者寫入後想看自己和大家的差異 DN You Draw It NYT、DN Climate Game FT（可擴充）
訊號 5：協作驗證 多人寫入、需要審核、有狀態變化（待審 → 已驗證 → 已公開） DN g0v 政治獻金透明、DN Documenting Hate ProPublica、DN 公民監督國會聯盟

二、反訊號：這些題目不需要資料庫

  • 故事是一次性事件，採訪結束就結束（適合滾動敘事）
  • 全部資料裝得進一個 CSV，不會再增長（用靜態 JSON 即可）
  • 讀者只看不互動，沒有寫入需求
  • 沒有版本變化，資料不會被更新或撤回

如果題目同時擊中 0 個訊號 → 純前端。1 個訊號 → 可選資料庫但非必要。2 個以上 → 應該用資料庫。

三、六種資料庫敘事模式（Pattern）

Pattern A：公開登記簿（Public Registry）

特徵：記者寫入、讀者只讀；資料持續累積；可逐筆查詢與聚合。

代表作（從本 wiki）： - DN The Force Report — 紐澤西警察武力資料庫（5 年 7 萬筆） - DN Trial and Terror Intercept — 全美恐怖主義訴訟資料庫 - DN Mass Killing Database USA Today — 全美大規模殺人事件資料庫 - DN ToxMap ProPublica — 全美工廠致癌空污地圖 - DN 六都選民看這裡 議員提案 — 議員提案資料庫 - DN 追蹤全臺區段徵收案 — 土地徵收資料庫

Firestore 結構：

collection: cases
  doc {id}:
    title: string
    location: GeoPoint
    date: timestamp
    category: string
    severity: number
    evidence_urls: string[]
    verified_by: string
    verified_at: timestamp

安全規則：read: true; write: if request.auth.token.role == 'reporter'

Pattern B：群眾投稿（Crowdsourced Reports）

特徵：讀者寫入、記者審核、通過後公開；有「待審 → 驗證中 → 已公開」狀態流。

代表作： - DN Documenting Hate ProPublica — 仇恨犯罪群眾投稿 - DN Lost Mothers ProPublica — 孕產婦死亡個案投稿 - DN g0v 政治獻金透明 — 雙人校對轉錄

Firestore 結構：

collection: submissions
  doc {id}:
    submitted_by: uid (anonymous OK)
    submitted_at: timestamp
    body: string
    contact: string (optional, encrypted)
    status: 'pending' | 'reviewing' | 'verified' | 'rejected'
    moderator_id: uid
    moderator_notes: string
    public_doc_id: string (link to /cases when verified)

安全規則：read: status == 'verified'; write: 任何 auth user; update: only moderators

Pattern C：即時事件追蹤（Real-time Tracker）

特徵：自動或半自動寫入、讀者即時讀取；前端用 onSnapshot 監聽。

代表作： - DN 2022 九合一地方公職人員選舉 — 即時開票 - DN Hot Disinfo from Russia — 俄語假訊息儀表板 - DN COVID Tracking Project — 志工每日更新疫情資料

Firestore 結構：

collection: events
  doc {id}:
    timestamp: timestamp
    source: string
    raw_data: map
    derived_metrics: map

collection: snapshots（聚合用）
  doc {YYYY-MM-DD-HH}:
    counts_by_type: map
    counts_by_region: map

安全規則：read: true; write: only via Cloud Functions（避免被偽造）

Pattern D：個人化記錄（Personal Log）

特徵：每個讀者有自己的歷史；用 anonymous auth 取得 uid。

代表作（可擴充）： - DN 餐桌上的碳排 出一張嘴救地球 — 加上「儲存我的飲食日記」 - DN Climate Game FT — 加上「我的決策歷史」

Firestore 結構：

collection: users / {uid} / meals
  doc {id}:
    items: [{name, grams, co2}]
    total_co2: number
    created_at: timestamp

collection: users / {uid} / decisions
  doc {gameSession}:
    choices: array
    final_score: number

安全規則：read, write: if request.auth.uid == userId

Pattern E：群眾比較（Compare with Crowd）

特徵：使用者寫入一個資料點，看到自己 vs 全體分布；後端要做 sampling/aggregation。

代表作： - DN You Draw It NYT — 你畫的曲線 vs 大家畫的 - DN 給你珊時萬 你想投給誰（可擴充）— 你的政治光譜 vs 大家的

Firestore 結構：

collection: drawings / {questionId}
  doc {submissionId}:
    points: [{x, y}]
    submitted_at: timestamp
    user_hash: string

collection: drawings_aggregate / {questionId}
  doc:
    p25: array
    p50: array
    p75: array
    sample_count: number
    last_updated: timestamp

安全規則：read: true; write: if request.auth != null；聚合用 Cloud Function 定時跑。

Pattern F：協作審核（Moderation Pipeline）

特徵：多角色寫入（投稿者、審核員、編輯）；資料有狀態與版本。

代表作： - DN g0v 政治獻金透明 — 雙人校對 - DN 公民監督國會聯盟 — 立委評鑑長期維護 - DN Documenting Hate ProPublica — 跨媒體編輯流

Firestore 結構：

collection: items
  doc {id}:
    raw_data: map
    transcribers: [uid1, uid2]
    versions: array of {by, at, content}
    consensus_status: 'pending' | 'matched' | 'conflict'
    final_data: map
    locked_by: uid (mutex)

安全規則：複雜，需要分角色與分階段；通常要 Cloud Functions 處理 transition。

五、Firebase 練習平台設定

為何 Firebase？

Firebase 功能 為什麼適合學生
Firestore NoSQL、即時監聽、不寫後端 code
Authentication 內建 Google / Email / 匿名登入
Hosting 一鍵部署靜態網站，免費 SSL
Cloud Functions 進階聚合、排程、moderation 自動化
Security Rules 用宣告式語法控制讀寫權限，比寫後端 endpoint 簡單
免費額度 Firestore 1 GiB 儲存 + 50K reads/day，學生作業夠用

30 分鐘設定流程

# 1. 安裝
npm install -g firebase-tools

# 2. 登入
firebase login

# 3. 建專案（也可在 [https://console.firebase.google.com](https://console.firebase.google.com) 開）
firebase projects:create digital-narrative-class

# 4. 初始化
mkdir my-project && cd my-project
firebase init
# 選: Firestore + Hosting + (optional) Functions

# 5. 部署
firebase deploy

前端最小範例（HTML + 純 JS）：

<!DOCTYPE html>
<html>
<head><meta charset="utf-8"></head>
<body>
<button id="btn">送出</button>
<ul id="list"></ul>

<script type="module">
import { initializeApp } from "https://www.gstatic.com/firebasejs/10.12.0/firebase-app.js";
import { getFirestore, collection, addDoc, onSnapshot, serverTimestamp }
  from "https://www.gstatic.com/firebasejs/10.12.0/firebase-firestore.js";

const app = initializeApp({/* your config */});
const db = getFirestore(app);

// 寫入
document.getElementById("btn").onclick = async () => {
  await addDoc(collection(db, "messages"), {
    text: "Hello",
    createdAt: serverTimestamp(),
  });
};

// 即時監聽
onSnapshot(collection(db, "messages"), (snap) => {
  document.getElementById("list").innerHTML = snap.docs
    .map(d => `<li>${d.data().text}</li>`).join("");
});
</script>
</body></html>

Security Rules 範本

// firestore.rules
rules_version = '2';
service cloud.firestore {
  match /databases/{database}/documents {

    // Pattern A: Public Registry — 所有人讀，只有 reporter 寫
    match /cases/{caseId} {
      allow read: if true;
      allow write: if request.auth.token.role == 'reporter';
    }

    // Pattern B: Crowdsourced — 任何登入者寫，moderator 改狀態
    match /submissions/{id} {
      allow create: if request.auth != null;
      allow read: if resource.data.status == 'verified'
                  || request.auth.uid == resource.data.submitted_by
                  || request.auth.token.role == 'moderator';
      allow update: if request.auth.token.role == 'moderator';
    }

    // Pattern D: Personal Log — 只能讀寫自己的
    match /users/{uid}/{document=**} {
      allow read, write: if request.auth.uid == uid;
    }

    // Pattern E: Compare with Crowd — 任何人寫一次，都能看聚合
    match /drawings/{qid}/submissions/{sid} {
      allow create: if request.auth != null;
      allow read: if false;  // 個別資料不公開
    }
    match /drawings_aggregate/{qid} {
      allow read: if true;
      allow write: if false;  // 只有 Cloud Function
    }
  }
}

六、五個學生練習（漸進難度）

每個練習都對照一件原作，先解析原作怎麼做（在 2022 年的工程脈絡下），再說明學生用 Firebase 的簡化路徑。Firestore schema + 關鍵 API 呼叫 + 安全規則 三件一起看。

練習 1：Hello CRUD（Pattern D，1 週）

題目：把 DN 餐桌上的碳排 出一張嘴救地球 擴充為「我的飲食日記」。讀者匿名登入、每天記錄飲食、看到自己 7 天碳排趨勢。

原作技術拆解

願景工程的版本是純前端：碳排係數寫死在 JS 物件、表單送出後 JS 計算總分顯示在頁面、離開頁面就消失。原作沒有後端、沒有跨日記憶、沒有「上次紀錄」。

學生升級的關鍵

從「一次性計算機」變成「個人記憶體」——使用者離開再回來看得到自己的歷史。這是 Pattern D 的本質：個人化的時間累積。

Firestore Schema
users/{uid}/meals/{mealId}
  date: timestamp           // serverTimestamp()
  items: [
    { name: "牛肉", grams: 200, co2_per_kg: 27.0 }
  ]
  total_co2: number          // 預先算好，避免每次重算
  created_at: timestamp
關鍵 API
import { signInAnonymously, onAuthStateChanged } from "firebase/auth";
import { collection, addDoc, query, where, orderBy,
         onSnapshot, serverTimestamp } from "firebase/firestore";

// 1. 匿名登入（取得 uid，跨刷新保留）
await signInAnonymously(auth);

// 2. 寫入今天的紀錄
await addDoc(collection(db, `users/${uid}/meals`), {
  items, total_co2, created_at: serverTimestamp()
});

// 3. 即時讀取近 7 天
const sevenAgo = new Date(Date.now() - 7*24*3600*1000);
const q = query(
  collection(db, `users/${uid}/meals`),
  where("created_at", ">=", sevenAgo),
  orderBy("created_at", "desc")
);
onSnapshot(q, snap => render(snap.docs.map(d => d.data())));
Security Rules
match /users/{userId}/meals/{mealId} {
  allow read, write: if request.auth.uid == userId;
}
驗收 + 進階
  • 驗收：新增 / 刪除紀錄、Chart.js 畫週趨勢、跨裝置同步（用 linkAccount 升級到 Google）
  • 進階：加 daily_aggregate 子集合儲存每日總分；加 streak 計算

練習 2：群眾登記簿（Pattern A，2 週）

題目：仿 DN The Force Report 做「校園機車違停登記」。學生記者拍照投稿、所有人可查地圖與單車格使用率排行。

原作技術拆解

NJ.com 的版本是靜態網站：記者用 5 年公文取得 7 萬筆 PDF → 內部資料工程師清洗成 CSV → 用 Astro / 11ty 生成 7 萬個靜態 HTML 頁面 → Algolia 提供搜尋。寫入是離線、一次性的；前端讀的是 build-time bundle，不是 live DB。

學生升級的關鍵

把「一次性靜態」變成「持續寫入」——記者用手機 web app 隨時投稿，不必重新 build。這是把 Pattern A 從「資料工程作業」轉成「即時記者工具」。

Firestore Schema
violations/{id}
  reporter_uid: string           // 寫入者 uid
  photo_url: string              // Firebase Storage URL
  location: GeoPoint             // (lat, lng)
  campus_zone: string            // "lib_west", "eng_back" 等
  vehicle_type: "scooter" | "bike" | "car"
  reported_at: timestamp
  verified: boolean              // 預設 false，moderator 設 true
  verified_by: string

zones/{zoneId}                   // 預先建好的單車格區域
  name: string
  polygon: array of GeoPoint
  legal_capacity: number
關鍵 API
// 上傳照片到 Storage 取得 URL
import { ref, uploadBytes, getDownloadURL } from "firebase/storage";
const photoRef = ref(storage, `violations/${uid}/${Date.now()}.jpg`);
await uploadBytes(photoRef, file);
const photo_url = await getDownloadURL(photoRef);

// 取定位 + 寫 Firestore
navigator.geolocation.getCurrentPosition(async pos => {
  await addDoc(collection(db, "violations"), {
    reporter_uid: uid,
    photo_url,
    location: new GeoPoint(pos.coords.latitude, pos.coords.longitude),
    campus_zone: detectZone(pos.coords),
    vehicle_type: form.vehicle_type.value,
    reported_at: serverTimestamp(),
    verified: false,
  });
});

// Mapbox 即時顯示已驗證點
const q = query(collection(db, "violations"), where("verified", "==", true));
onSnapshot(q, snap => updateMapMarkers(snap.docs));
Security Rules（Custom Claims for reporter role）
match /violations/{id} {
  allow read: if resource.data.verified == true
              || request.auth.uid == resource.data.reporter_uid;
  allow create: if request.auth.token.role == 'reporter';
  allow update: if request.auth.token.role == 'moderator';
}

要在 Firebase Admin SDK 中對 reporter 帳號設 custom claim：

await admin.auth().setCustomUserClaims(uid, { role: 'reporter' });
驗收 + 進階
  • 驗收：投稿頁、地圖頁（聚合到 zone）、單車格使用率排行（過去 7 天 / 30 天）
  • 進階：用 Cloud Function 偵測重複投稿（同地點 5 分鐘內）；EXIF 校驗照片時間戳

練習 3：群眾投稿 + 審核（Pattern B，2-3 週）

題目：仿 DN Documenting Hate ProPublica 做「校園不當對待提報」。匿名提交 → 編輯審核 → 通過後公開摘要。

原作技術拆解

ProPublica 的版本是 Airtable + 自製驗證 dashboard：投稿表單寫入 Airtable → 編輯團隊在 Airtable 內標 status → 通過的案件用 Airtable API 同步到公開資料庫。多家媒體 100+ 編輯共用同一個 Airtable。狀態流：incoming → reviewing → verified → published 或 rejected。

學生升級的關鍵

把 Airtable 換成 Firestore，用 status 欄位 + security rules 把投稿者與審核者徹底分權——投稿者只能讀自己的、審核者讀全部、公眾只能讀 verified 後的摘要文件。狀態機是這個 Pattern 的核心。

Firestore Schema（雙集合分權）
submissions/{id}                 // 原始投稿（含敏感資料）
  submitted_by: uid (匿名 OK)
  submitted_at: timestamp
  body: string                   // 完整描述
  contact: string                // 加密儲存
  evidence_urls: string[]
  status: 'pending' | 'reviewing' | 'verified' | 'rejected'
  moderator_id: uid
  moderator_notes: string
  public_doc_id: string          // 通過後指向 /cases

exports.verifySubmission = functions.https.onCall(async (data, ctx) => {
  if (ctx.auth.token.role !== 'moderator') throw new Error('forbidden');

  const caseRef = db.collection('cases').doc();

      type: data.type,
      summary: data.summary,
      source_submission_id: data.id,
      published_at: admin.firestore.FieldValue.serverTimestamp(),
    });
  });
});

練習 4：即時儀表板（Pattern C，2 週）

題目：仿 DN 2022 九合一地方公職人員選舉 做「校園投票即時開票」或「校慶活動人流監測」。資料來源：學生會 Google Form 或定時抓 API。

原作技術拆解

READr 的版本是 後端 SSE / WebSocket 推播：中選會 API 每 30 秒更新一次 → READr 後端 polling → 用 SSE 推給前端 → Mapbox 重繪。前端不直接連中選會（CORS + rate limit），所有 ETL 都在後端。

學生升級的關鍵

Firestore 的 onSnapshot 已內建即時推播——完全省掉 SSE / WebSocket 程式碼。寫入端用 Cloud Function scheduled 每 5 分鐘抓一次資料源並寫入 Firestore，前端訂閱即可。這是 Firebase 對學生最殺的優勢。

// functions/index.js
exports.aggregateEvery5min = functions.pubsub
  .schedule('every 5 minutes')
  .onRun(async () => {
    // 1. 抓資料源（Google Form Sheet 或 API）
    const newEvents = await fetchFromSource();
    const batch = db.batch();
    newEvents.forEach(e => {
      batch.set(db.collection('events').doc(), {
        timestamp: admin.firestore.Timestamp.fromDate(e.ts),
        source: 'student_council_form',
        raw: e,
        derived: { candidate_id: e.choice, location_zone: e.zone },
      });
    });
    // 2. 寫入聚合
    const snapId = new Date().toISOString().slice(0, 16);
    batch.set(db.doc(`snapshots/${snapId}`), {
      total_count: newEvents.length,
      by_candidate: groupBy(newEvents, 'choice'),
      by_zone: groupBy(newEvents, 'zone'),
      generated_at: admin.firestore.FieldValue.serverTimestamp(),
    });
    await batch.commit();
  });

練習 5：你畫看看（Pattern E，3 週）

題目：仿 DN You Draw It NYT 做台灣版。讀者先畫「2015-2025 台灣出生人口」的猜測曲線，提交後看到真實答案 + 自己的線 + 群眾分布（p25/p50/p75 帶）疊加。

原作技術拆解

NYT Upshot 版用的是 D3 + 後端聚合 endpoint：讀者用 SVG drag 畫線 → POST 到後端 → 後端把點存到資料庫 + 預先計算好的 p25/p50/p75 帶回傳。每個讀者只看到聚合，不看到別人的個別曲線（隱私 + 載入量）。

關鍵設計：個別曲線寫進去就鎖起來（讀不到），只有聚合是公開的。

學生升級的關鍵

這是 6 個 Pattern 中最考驗 schema 設計的，因為涉及： 1. 大量寫入（萬人投稿） 2. 聚合計算（不能每次 query 都重算 p25/p50） 3. 分權（個別不公開，聚合公開）

Firestore Schema（關鍵：分集合）

  title: string
  x_label: string
  y_label: string
  x_range: [2015, 2025]

// Cloud Function：每 N 筆或每小時重新計算聚合
exports.aggregateDrawings = functions.firestore
  .document('drawings/{qid}/submissions/{sid}')
  .onCreate(async (snap, ctx) => {
    const { qid } = ctx.params;
    const all = await db.collection(`drawings/${qid}/submissions`).get();
    if (all.size % 10 !== 0) return;     // 每 10 筆才重算

    // 對每個 x，蒐集所有 y，計算分位數
    const xs = all.docs[0].data().points.map(p => p.x);
    const aggregate = xs.map(x => {
      const ys = all.docs.map(d =>
        d.data().points.find(p => p.x === x).y
      ).sort((a, b) => a - b);
      return {
        x,
        p25: ys[Math.floor(ys.length * 0.25)],
        p50: ys[Math.floor(ys.length * 0.50)],
        p75: ys[Math.floor(ys.length * 0.75)],
      };
    });
    await db.doc(`drawings_aggregate/${qid}`).set({
      sample_count: all.size,
      p25: aggregate.map(a => ({ x: a.x, y: a.p25 })),
      p50: aggregate.map(a => ({ x: a.x, y: a.p50 })),
      p75: aggregate.map(a => ({ x: a.x, y: a.p75 })),
      last_updated: admin.firestore.FieldValue.serverTimestamp(),
    });
  });

七、評分指標

維度 高分（80+） 中分（70-79） 低分（<70）
資料庫必要性 切中 2+ 個訊號 切中 1 個訊號 純前端就能做
Firestore 結構設計 集合與欄位映射清晰，能擴充 能跑但結構鬆散 結構錯誤導致查詢困難
Security Rules 寫入路徑分角色、有審核 基本登入檢查 全開或全關
使用者體驗 寫入回饋即時、錯誤處理完整 能寫入但回饋弱 寫入後不知是否成功
倫理與隱私 投稿同意、資料最小化、可刪除 有聲明 無同意機制

八、常見坑與避雷

  • 資料量爆炸：Pattern E 如果存 10 萬筆讀者曲線，列表 query 會超出 quota。解法：聚合到 _aggregate 集合，個別資料只用 Cloud Function 寫入
  • 沒寫 security rules：Firebase 預設 30 天測試模式之後就全鎖。解法：上線前一定要部署 rules
  • 匿名登入沒清理：每位讀者都成新 uid，資料無法跨裝置同步。解法：教 linkAccount，把匿名升級成 Google
  • 時區地獄：用 serverTimestamp() 而不是 new Date()，避免讀者本地時鐘不準
  • moderation 工作量低估：Pattern B 上線後審核排隊。解法：先設 100 件上限或封閉測試
