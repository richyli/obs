  • 為什麼今天要請大家裝 VS Code + Claude Code，而不是繼續開瀏覽器聊天？

一句話定義

Agentic AI = 會主動拿工具、改檔案、跑程式、串外部服務的 AI——不只是回你一段文字，是在你的電腦上替你做事。

對比一下：

對話式 AI（ChatGPT 網頁版） Agentic AI（Claude Code）
它做什麼 回你字串 讀檔、改檔、跑指令、串 API
你做什麼 複製貼上 看它做、必要時喊停
出錯時 你重貼一次 它自己跑下一步修
一個 prompt 換來 一段答案 一連串動作 + 一段答案

為什麼現在要談這個

兩件事在 2025–2026 之間成熟：

  1. 模型夠強到可以放手——Opus 4.x、Sonnet 4.x 的工具使用（tool use）穩定到可以連續做 20–30 步不爆掉。
  2. harness 成熟——Claude Code、Cursor、Windsurf 這類 CLI / IDE 整合，把「模型 ↔ 你的檔案系統 ↔ 你的瀏覽器 ↔ 你的行事曆」串起來（「harness」這個詞 S4 會詳講）。
  3. 開始進入了不跟上會落後的階段

今天的重點不是學新 prompt 技巧，是學「怎麼把一件事的決策權交給 AI、但又不會失控」。

用「員工」來比喻

把 AI 想成你雇的員工：

  • 對話式 AI 是個「能力強但很笨」的新人：問什麼答什麼、知識淵博，但每天上班都失憶——不認得你的檔案、不記得你昨天交代過什麼、不知道你討厭破折號、不知道你下週要交什麼東西。你每次都得從頭交代。
  • Agentic AI 是個「跟你工作三年的助理」：認得你公司的檔案系統、記得你的習慣（不放糖、不寫破折號、報告先給結論）、知道哪些事該自己處理、哪些要先問你。你交代「幫我準備明天會議資料」，他自己去翻、整理、放好。

今天下午要做的事，就是把第二種員工從零訓練起來。

我的真實例子：/today 與 /daily 兩個 skill 的分時段差異

我每天有兩個核心 skill，分早晚兩次跑。先把它們的差異講清楚——這是後面所有討論的場景錨。

/today：當天工作排程，早晚各跑一次

  • 早上 8:00 跑：掃 todo/ 所有 Todo: true 的任務 → 依 Deadline + Priority 排序 → 產出今天該做的清單到 Obsidian Kanban
  • 晚上 22:00 跑：讀我白天手動拖過的 Kanban 卡片（拖到「✅ 完成」/「📅 明日 deliver」等欄）→ 把拖動結果寫回每個 task 的 YAML → 重建明日清單
  • 主要介面：todo/Todo Kanban.md（7 欄看板，🔴 今日確定處理 / 📅 明日 deliver / 🟡 本週推進 / 🔥 重要待排程 / 📦 之後再做 / 🗄️ 深櫃 / ✅ 完成）
  • 特性：雙向同步——我拖卡片，Claude 寫回 YAML；YAML 改了，Claude 重畫 Kanban
  • 跑完還會繼續：產 70 則新聞 + 4000 字 brief（/news-sec）、抓 Yahoo Japan 寫 N4/N5 日語教材（/jp-daily）、抓 Polar 手錶睡眠資料（/sleep-report）、綜合 Google Calendar、更新番茄鐘。

/today 解決的問題：把「我心中的優先順序」與「實際工作流程」每天對齊兩次。

/daily：早上跑一次的維護流水線

/daily 才是真正讓我「沖咖啡的時間自動跑完一切」的那個。它是個多 subagent DAG（有向無環圖），依序跑 10 個 step，每個 step 都丟給獨立的 subagent 在自己的 context 裡跑、跑完只回主對話一段摘要：

1. /read-citavi      ← 讀 Citavi 新 PDF（上限 6 篇）寫成 wiki note
   └─ 1.5 /journal-watch  ← 每 7 天跑：掃學術期刊 TOC
       └─ 1.6 /weekly         ← 每週日跑：週維護
           └─ 2. /extend       ← 擴充需要展開的 note
               └─ 3. /methodology   ← 整理方法論 note
                   └─ [4. /summary-note] ‖ [5. /random-link]  ← 並行
                       └─ 6. /book-edit       ← 更新 16 本研究手冊
                           └─ 7. /scholar      ← 識別並建立學者 note
                               └─ 8. /audit    ← 全 vault 品質檢查
                                   └─ 9. /daily_report  ← 產出今日綜合報告
                                       └─ 10. /wish-list  ← 未完願望清單

特性：單向——/daily 是「主動推送」型 skill，跑完把結果擺到你眼前；你不需要互動、不需要拖卡。

為什麼要分兩個

比較項 /today /daily
跑的頻率 一天 2 次（早 + 晚） 一天 1 次（早上）
與我互動 我拖卡片、它寫回 YAML 我不需要動、只看結果
主功能 任務排程 + Kanban 雙向同步 知識庫維護 + 內容供給（新聞 / 論文 / 教材）
失敗代價 排錯一天 漏讀幾篇論文、新聞
跑完誰看 我看 Kanban 規劃 Claude 寫完進對應資料夾，我有空再看

簡單講：/today 是「我的祕書」、/daily 是「我的研究助理」。一個管我的時間，一個管我的學術產出。

整個過程我沒有打字，就是 /daily 一個指令。早上沖咖啡的時間它跑完了。

這就是今天下午要讓大家感覺到的東西——授權給 AI，而不是指揮AI。

為什麼從 Claude Desktop 切到 Claude Code

本地端環境的 Claude Code 的特點：

  1. 看到你的檔案：Claude Code 直接住在你的專案資料夾裡，能 Read、Edit、Write、Glob、Grep 你的整個 codebase / 專案資料庫。

  2. 存你的習慣：Claude Code 有 CLAUDE.md（專案規則）、memory/（跨對話記憶）、skills/（封裝指令），三層記憶會跟著你一直長大。

CLAUDE.md：給這個專案的「公司守則」

CLAUDE.md 就放在你專案根目錄的一個 markdown 檔。每次你在這個資料夾打開 Claude Code 對話，這份檔的內容會自動被讀進去——不用你提醒，可以視為公司的規範。

我的 CLAUDE.md 開頭有一條鐵律：「每次回應結束前，必須把使用者本次的需求登記到 wiki/user_requests_log.md」。所以不管我今天叫它做什麼，結束前它都會去更新那份 log，不需要我每次喊一遍。

寫 CLAUDE.md 的時機： - 這個專案有特殊的檔案結構要它遵守（例：「所有筆記只能寫在 wiki/ 內」） - 這個專案的對話有固定產出格式（例：「commit message 用繁體中文 + 動詞開頭」） - 這個專案有絕對禁區（例：「不可動 published/ 目錄」）

Memory：跨對話、跨專案的「個人偏好」

memory/ 跟 CLAUDE.md 不同——CLAUDE.md 綁專案，memory 綁你這個人。我的 memory/ 現在有 30+ 條，例如：

  • 「中文不要用破折號插入語」
  • 「研究樣本只能台灣，不可設計跨國研究」
  • 「PDF 圖片偽影直接刪不要問」

讓 Claude Code 記憶有兩種方式： 1. 你說「記下來」：講完糾正後加一句「把這個寫進 memory」，它會自己存檔。 2. 它主動觀察：Claude Code 內建一條 auto memory 規則，當你反覆糾正同一件事，它會主動寫進 memory。

跨機呼叫：memory 檔放在你的 ~/.claude/projects/<project>/memory/。如果你的 home 目錄有同步到 Dropbox / OneDrive（我自己是把整個 .claude/ 同步），在公司電腦和家裡筆電打開 Claude Code，會讀到同一份記憶。沒同步的話換機器就會失憶——這是大家最容易踩的坑。

我的多機同步真實歷程（直接交給 Claude Code 處理）

我自己有兩台 Windows 電腦（家裡一台、辦公室一台）+ 同一份 Dropbox。每次換機器要做的事很多：memory 對齊、.claude/skills/ 同步、過去 session 紀錄要能撈到、本機自動化腳本（番茄鐘、開機啟動）要兩台一致、本機 Junction 連結要重建 ……

這些我沒有自己研究過一次。流程是：

  1. 在新機器打開 Claude Code，第一句講：「我這台機器是新的，幫我比對另一台跟這台的 .claude/ 設定差在哪、補齊」
  2. 它自己跑 Glob、Read、diff，列差異給我
  3. 我說「OK 全部補齊」，它寫個一次性腳本跑完
  4. 遇到 Windows 特殊狀況（例：Junction、Startup 捷徑、Dropbox 路徑大小寫）它會問我一兩題、我回答完就繼續

Skills

第三層是 skills——這留到 S5 詳講。先記住：CLAUDE.md 管「這個專案的規矩」、memory 管「你這個人的習慣」、skills 管「你常做的動作」。

基本邏輯：Claude Code 一次回應在做什麼

你打一句話
  ↓
模型決定要不要先用工具（Read / Bash / Grep / WebFetch ...）
  ↓
工具回傳結果給模型
  ↓
模型可能再叫一次工具（迴圈）
  ↓
模型給你最終回應

關鍵字：tool use loop。模型可以連續呼叫工具直到它覺得問題解了，再回你一段話。

harness 是什麼

harness 直譯是「馬具」「韁繩」。在 AI 圈，harness = 把模型套上工具、權限、檔案系統的整套外掛。

模型本身（Opus 4.7、Sonnet 4.6）只是一個吃 token 吐 token 的引擎。它怎麼「呼叫工具」？怎麼「讀你的檔」？怎麼「記住你的 memory」？怎麼「跑 Bash」？怎麼在 context 滿了的時候自動 compact？——這些都不是模型本身的功能，是 harness 提供的。

主流 harness： - Claude Code（Anthropic 官方）：今天用的 - Cursor：VS Code fork + 內建 chat - Windsurf：Codeium 出的 - Cline / Continue：開源的 VS Code 擴充

同一個模型套不同 harness 行為差很多。Claude Code 強在：原生 Skill 系統、原生 MCP 串接、/agents 多代理人、Bash sandbox。所以今天選它當主要工具。

Token 是什麼

講 context 之前，要先講 token——AI 圈最常聽到、卻最少人講清楚的單位。

Token = 模型處理文字的最小單位。不是字、不是詞、不是 byte——是介於字與詞之間的小塊。例：

原文 切成 token
Hello world ["Hello", " world"] 2 個 token
Agentic AI ["Ag", "entic", " AI"] 3 個 token
你好 ["你", "好"] 2 個 token
今天天氣很好 ["今天", "天", "氣", "很", "好"] 5 個 token

粗略換算（英文 vs 中文差很多）：

  • 英文：1 token ≈ 0.75 個英文字（即 4 個英文字母 ≈ 1 token）
  • 中文：1 token ≈ 0.5–0.7 個漢字（中文每字資訊密度高，1 個漢字常拆 1–2 個 token）

所以同樣 1000 個 token：英文約 750 字，中文約 500–700 字。

為什麼要懂 token

三個原因：

  1. 計費單位：Claude / OpenAI / Gemini 通通按 token 計價（input token 一個價、output token 另一個價，後者通常貴 4–5 倍）。你跑 /daily 燒幾塊錢，就是燒 token。
  2. Context 上限：每個模型有「一次對話最多吃幾個 token」上限——Opus 4.7 是 1M token（約 75 萬字英文 / 50 萬字中文）。塞滿就裝不下、會被自動壓縮。當Context越大，回應效率與品質就愈差。
  3. 速度：你給模型的 prompt 越長（token 越多），它每次回應前要「讀」的時間越久。所以 context 不是越塞越好。

省 token 的常識：別讓 Claude 讀整個資料夾如果只需要 3 個檔；別把整份 PDF 貼進對話如果只要查一個段落；複雜任務拆 subagent，分身吃完丟掉、不污染主對話。

Context 是什麼，為什麼重要

「Context」= 這次對話模型「看得到」的所有 token，包含：

  • 系統提示（Claude Code 本身的 instructions）
  • CLAUDE.md 的內容
  • memory/MEMORY.md 索引
  • 你前面打的每一句話 + 它前面回的每一段
  • 它讀過的每個檔案的內容
  • 每次工具呼叫的結果

context 有上限（Opus 4.7 是 1M token，約 50 萬字中文，但塞滿會變慢、變貴、變笨）。所以你要學會：

  • 小事用小 context（單檔修改別讓它 Glob **/*.md）
  • 大事拆 subagent（用 Agent tool 開分身去查，分身做完只回主對話一段摘要，不污染主 context）。
    • 可以在 Skill 設計時，要求多 Agent 執行。或者將 Skill 拆小，觸發後也會用 Sub-Agent 的方式進行。

案例：/today ← /kanban ←—— skill 不只一種等級

延續上面的「拆小、用 sub-agent」。我自己有兩個關係很緊的 skill，剛好示範「skill 微小化」的真實用途：

/today /kanban
角色 「規劃」型 skill 「同步」型 skill
跑什麼 Kanban 同步 + 抓 Google Calendar + 跑 /news-sec + /jp-daily + /sleep-report + 7 日展望 + 子任務拆解 + 互動勾選 只跑 read_kanban() → write_kanban() → write_project_kanbans()
耗時 2–5 分鐘 1–3 秒
何時用 早上開工、晚上收工這兩個關鍵時點 白天任何時候拖了卡片、勾了完成、想立刻看更新

為什麼要拆

如果只有 /today——白天我每改一張卡都得等 2 分鐘讓它跑完整套，痛苦。所以我把 /today 裡最頻繁、最輕的子流程獨立成 /kanban，3 秒就跑完。

這就是 agent 微小化（agent minimization） 的真正用途——把一個大 skill 內部「最常被單獨呼叫的部分」抽出來，做成獨立 skill。

判斷準則：什麼時候該把子流程拆成獨立 skill？

問三題：

  1. 這段子流程的功能，會被「單獨」需要嗎？（如果只在大 skill 內部呼叫、外部用不到 → 不用拆）
  2. 它跑起來輕嗎？（如果輕 → 拆出來，讓使用者可以高頻呼叫；如果重 → 跟大 skill 一起跑沒差）
  3. 它有副作用嗎？（讀取型 → 安全可拆；寫入型 → 拆出來小心併發衝突）

/kanban 三題都 yes（單獨會用、3 秒輕、寫入但只動 YAML 沒併發問題）→ 值得拆。

對比 /daily 為什麼不拆

S1 提過的 /daily 是 10-step subagent DAG（讀 Citavi、跑 extend、跑 scholar、跑 audit ……），裡面每個 step 已經是獨立 skill 了（/read-citavi、/extend、/scholar、/audit）。/daily 只是把它們串成一個 pipeline——這跟 /kanban 從 /today 拆出來是相反方向。

兩個方向都有用： - 由大拆小（/today → /kanban）：給高頻單一動作一個獨立 entry - 由小串大（/read-citavi + /extend + /scholar + ... → /daily）：給低頻組合動作一個批次 entry

你寫 skill 寫到第 5、第 6 個會自然遇到這兩個方向，提早知道有這兩條路，比較不會卡住。

專案 / 對話 / Context 三層的差異

容易混。一句話對照：

層 是什麼 範圍 結束時機
專案（Project） 一個資料夾 + 它的 .claude/ 設定 跨多次對話 你刪掉資料夾
對話（Conversation） 你跟 Claude 的一輪互動 一次開機 你打 /clear 或關掉視窗
Context 這一輪對話模型「看得到」的所有文字 對話內 上限到了會自動壓縮

所以：你在同一個專案開 10 次對話，會共享 CLAUDE.md 和 memory/，但每次對話的 context 是獨立的——上一次它讀過的檔，下一次得重讀。

Hand off：對話太長怎麼辦

當 context 快滿（看下方百分比），有兩種交棒方式：

  1. /compact：叫 Claude 把目前對話自己摘要成一段精簡版本，下半場帶著摘要繼續。簡單問題夠用。
  2. 手動 hand off：叫它寫一份「下一個 session 接手指南」（什麼做完了、卡在哪、下一步要做什麼），存成 markdown 檔。新對話開起來，第一句叫它 Read 那份指南。複雜任務一律用這招——/compact 會漏關鍵細節。

我自己每次 /daily 跑到一半 context 滿了，就會生一份 handoff.md，下午再開新對話接續。

Glob 是什麼

Glob 是 Claude Code 內建的檔案搜尋工具，吃萬用字元（wildcards）。例： - **/*.md ＝ 所有資料夾下所有 .md 檔 - wiki/news*.md ＝ wiki/ 下檔名以 news 開頭的 .md - 2026-*/report.pdf ＝ 2026-開頭資料夾下的 report.pdf

用途：當你說「掃我所有 todo 檔」，Claude 第一步就是 Glob 把候選清單抓出來，再逐一 Read。比 Mac/Windows 的搜尋快很多，因為它只列檔名不開檔。

Bash 是什麼（含 PowerShell 與 Claude Code 的關係）

先把三個詞的關係講清楚——很多人卡在這。

Bash / PowerShell / Claude Code 三層關係

名詞 是什麼 你過去看過它嗎？
PowerShell Windows 內建的命令列環境（黑底白字、會打 dir、cd 的那個視窗） 看過——按開始鍵打「powershell」就跳出來
Bash 原本是 Unix / Linux / Mac 的命令列環境，後來移植到 Windows（git-bash、WSL） Windows 用戶通常沒看過，Mac 用戶天天用
Claude Code AI 助理，需要透過某個命令列環境去執行指令 今天剛裝的

簡單講：PowerShell 跟 Bash 是兩種不同的「命令列方言」，做的事差不多（列檔、刪檔、跑程式），但語法略有差異（例：清螢幕 PowerShell 打 cls、Bash 打 clear）。

Claude Code 需要一個命令列環境來跑 git status、python script.py 這類指令——它自動偵測你的系統用哪個：

  • Windows 用戶（我自己）：Claude Code 預設用 PowerShell（你裝 git 時也會一併裝 git-bash，部分指令會 fallback 到 git-bash）。我整份講義所有 demo 都是 PowerShell 環境跑的。
  • Mac 用戶：Claude Code 用 zsh（macOS 預設）或 Bash——這兩個語法 99% 相通，Mac 學員直接用就好，不需要任何額外設定。
  • Linux 用戶：跟 Mac 一樣，預設 Bash / zsh。

⚠️ 我自己沒有 Mac 環境，所以講義裡的截圖、路徑（d:/Dropbox/...）、指令格式都是 Windows / PowerShell 版本。Mac 學員看到的時候自行對照：

我的 Windows 寫法 Mac 對應
d:/Dropbox/Zettel/... ~/Dropbox/Zettel/...
~/.claude/ ~/.claude/（一樣）
PowerShell 開檔：notepad file.md Mac 開檔：open file.md
python script.py python3 script.py（Mac 預設 python 還指 2.x）

Claude Code 本身在 Mac 上跑得完全沒問題——是 Anthropic 跨平台官方工具，今天教的所有概念（CLAUDE.md / memory / skill / MCP）在 Mac 完全一致，差別只在底下那層命令列方言。

回到 Bash 工具的用途

不管你的系統實際用 PowerShell 還是 Bash，Claude Code 的工具名稱統稱 Bash。例： - git status 看 git 狀態 - python script.py 跑 Python 腳本 - curl ... 抓網頁

任何「不只是讀檔、要實際執行什麼」都靠這個工具。我跑 /sleep-report 時，Claude 就用它呼叫 Python 去抓 Polar 手錶的 API。這是 Claude 從「文字機器」變「會做事的助理」的關鍵介面。

Demo：Google Calendar 串接 + 個人小祕書

現場 demo（≈ 5 分鐘）：

  1. 在 Claude Code 裡輸入「幫我看下週有幾個會、哪天最空」
  2. 它呼叫 mcp__claude_ai_Google_Calendar__list_events
  3. 回你一張表 + 建議哪天約新會議
  4. 接著我說「禮拜三下午幫 Iona 開一個 1 小時的 follow-up」
  5. 它呼叫 mcp__claude_ai_Google_Calendar__create_event，跳出確認、按 Enter，會就建好了

串接步驟（claude.ai Connectors 路線，3 分鐘搞定）

這是最快的路——不用裝任何東西，在 claude.ai 網頁設定一次，Claude Code 在本機就能用。

Step 1：打開 claude.ai，登入你今天付費的帳號（同一個帳號）。

Step 2：右上角頭像 → Settings → 左欄找 Connectors（或 Tools → Connectors，介面偶爾調整）。

Step 3：列表裡找 Google Calendar，點 Connect。

Step 4：跳出 Google 授權頁——選你的 Google 帳號 → 同意它讀取 / 建立行事曆事件 → 跳回 Claude。Connector 狀態變成「Connected」。

Step 5：回到本機 VS Code 的 Claude Code，輸入「幫我看下週的行事曆」——它會自動偵測到 mcp__claude_ai_Google_Calendar__list_events 這個工具可用，直接呼叫。

注意事項：

  • 同一個帳號：claude.ai 網頁與你 Claude Code 登入的 Anthropic 帳號要一致，不然 connector 抓不到。
  • 第一次呼叫會跳確認：Claude Code 會問「要不要允許這次工具呼叫」——按 Y。可以選 「Always allow」省麻煩。
  • 隱私：connector 是 OAuth 授權，Anthropic 不存你的行事曆內容，只在這次對話傳輸。

進階：同一路徑可以連 Gmail、Google Drive、Spotify。我現在連了 4 個——每天 /daily 自動讀行事曆、寄睡眠報告到自己信箱。

這就是 agentic 的感覺：你描述意圖（不是步驟），它選工具、它執行、它確認。

🧑‍💼 企業主的思考時間

剛剛 demo 的 Google Calendar 串接，背後叫 MCP（Model Context Protocol）——讓 AI 跟外部服務對話的通用標準。Anthropic 在 2024 推出，現在 OpenAI、Google 都採用了。

想想看——

  • 盤點外部服務：你今天公司用的雲端工具（CRM、ERP、HR、會計、雲端硬碟），哪些已經有 MCP 可以串？哪些還沒有？
  • 沒有 MCP 的服務，你會考慮替換成有 MCP 的對手嗎？還是請 IT 自己搭一個？
  • 自家內網系統（內部 ERP、客戶資料庫、知識庫），要不要主動做一個內部 MCP？
  • 反向：你的公司對外能提供 MCP 嗎？如果客戶的 AI 想直接讀你的產品目錄 / 帳戶餘額 / 貨況，你準備好了嗎？
  • 這跟當年「要不要做 API」「要不要做 App」是同一類問題嗎？時間窗口會多長？

補：Python 是什麼？跟 Claude 是什麼關係？

非工程背景看到 .py 會緊張——其實不用。

Python 是什麼

一種程式語言，1991 年發明，今天全世界 AI / 資料分析 / 自動化最主流的語言。特點：寫起來像英文 + 標點符號很少。例：

for file in files:
    if "report" in file:
        print(file)

讀起來：「對 files 裡每個 file，如果 file 名含 'report'，印出來」——就是英文。所以即使你不會寫，讀起來也猜得出在做什麼。

Python 之所以變主流，是因為它有大量現成套件（別人寫好的工具庫），你想做什麼幾乎都有人寫過： - 抓網頁 → requests - 處理 Excel → pandas - 畫圖 → matplotlib - 跑 AI 模型 → transformers - 處理 PDF → pypdf

裝一行（pip install pandas）就能用。

Claude 跟 Python 是什麼關係

三層：

  1. Claude 自己會寫 Python：你叫它「寫一個腳本抓 Polar API 的睡眠資料」，它寫得出來、會 debug。
  2. Claude 用 Bash 跑 Python：你的 skill 寫「python tools/sleep_report.py」這行，Claude 就會用 Bash 工具呼叫 Python 跑這支腳本。
  3. Python 幫 Claude 做它不擅長的事：模型不擅長精確算數、批次處理一萬個檔。把這些「機械活」寫成 Python script，模型負責「想」、Python 負責「做」——分工合作。
  4. 省掉 Token 費用，在本地端運算。

對非工程背景的你：

  • 不用學 Python 寫法——叫 Claude 幫你寫，你只要看得懂 README 怎麼跑
  • 要會的：知道你電腦有沒有裝 Python（Windows：開 PowerShell 打 python --version，有版號就有裝；沒有的話請 Claude 教你裝）
  • 進階：兩三個月後你會自然看懂 Claude 寫的 Python，因為它寫的程式都會加註解、命名清楚

我不會寫 python，但現在我的 tools/ 累積 30 多支腳本（睡眠分析、新聞抓取、wiki 維護、SNA 計算、YouTube抓取），99.99 % 是 Claude 幫我寫的。我只負責提需求、看結果、講錯哪。

Claude 自己不寫複雜運算——它呼叫已經寫好的 script。為什麼這樣設計：

  1. 可靠：純計算交給 Python 比較不會出錯，模型不擅長精確算數
  2. 快：script 直接跑比模型一邊讀一邊算快 10 倍
  3. 可重跑：你不開 Claude Code 也能直接 python tools/sleep_report.py 跑

寫 skill 的判斷： - 文字、判斷、寫作 → 全寫在 SKILL.md，讓模型直接做 - 數學、API、檔案批次處理 → 寫成 script，SKILL.md 只負責叫它跑

不會寫 Python 沒關係——叫 Claude Code 幫你寫。「我要一個腳本能從 Polar API 抓 HRV 資料」，丟給它，它寫完、debug 完，放進 tools/，再幫你寫好 SKILL.md。整個流程你都不用打程式碼。

怎麼自動化

兩條路：

A. Cron 排程：設定固定時間自動跑。例：每天早上 7:00 自動跑 /news-sec，咖啡來不及泡完，70 則新聞已經彙整好了。

B. Hook 觸發：在 Claude Code 的 settings.json 裡寫 hook，當某事件發生（例如 Stop = 對話結束），自動執行某個指令。例：每次對話結束自動跑 /log-request，把這次需求登記到 wiki/user_requests_log.md。

設計時問自己三個問題： 1. 這個 skill 的輸出，使用者會不會用某種動作回應？（讀完？刪掉？標記？轉發？） 2. 那個動作能不能存成可讀的訊號？（checkbox、檔案移動、tag 修改） 3. 下次跑這個 skill 時，能不能先讀那個訊號？

三個 yes，恭喜，你的 skill 會自己成長。

S7 ｜ 知識庫實作：用 Obsidian 建構（15:50, 20 min）

為什麼是 Obsidian

「知識庫」這三個字聽起來很大，但其實只需要兩件事：

  1. 一堆 markdown 檔放在一個資料夾
  2. 檔案之間用 wikilink 互相連起來

Obsidian 就是把這兩件事做到極致的編輯器。它不是雲端服務——你的 專案資料庫 就是一個本機資料夾（我的放在 Dropbox 同步）。這意味著：

  • Claude Code 可以直接讀寫
  • 你的資料沒有鎖在第三方服務裡
  • 你關掉 Obsidian、用任何 markdown 編輯器都能看

以員工的角度來看：

  • 直接請AI回答，AI就是沒有看資料庫就回答的員工（Zero Shot）
  • 建立個人知識庫，就等於跟員工說：「你去查了資料回來再跟我說！」（氣氣氣）

🧑‍💼 企業主的思考時間

知識庫是公司最低調但最值錢的資產之一——

  • 你公司現在的「知識庫」長什麼樣？SharePoint？Notion？還是「在資深員工腦袋裡」？
  • 如果搬到 markdown + wikilink 的形式，誰要負責維護？是 CKO（Chief Knowledge Officer）？還是每個員工都有自己一塊責任田？
  • 客戶資料、內部 know-how、過往專案——這些都要 AI 看得到嗎？哪些設權限隔離？
  • 能不能對外賣？把公司知識庫的一部分包成 MCP / API 賣給上下游或客戶——這是新的營收來源還是知識外洩？
  • 一年後員工帶走的不再是「Excel + Word」，而是「他整理過的 專案資料庫」。你的離職交接流程準備好了嗎？

我的 專案資料庫 規模（給大家一個尺度感）

  • 18,000+ 個 markdown 檔
  • 主要在 wiki/ 目錄
  • 每篇都有 YAML frontmatter：tags、date、extend、degree（SNA 計算）、cluster（Louvain 分群）

為什麼要連起來

  2. AI 看得到關聯：當 Claude Code 讀一篇 note，它順著 wikilink 可以拉相關 5–10 篇，得到完整脈絡。
  3. Agent 訓練成你喜歡的樣子

我的 Skill 檢查流程：用 /skill-review 讓 skill 自我體檢

skill 寫多了會發現：你在對話裡反覆做的事，就是 skill 沒做好的事。我寫了一個 meta-skill 叫 /skill-review，每隔一段時間跑一次，讓系統自己找出哪些 skill 該升級。

它的步驟（節錄真實 SKILL.md）：

步驟一：讀 user_requests_log.md 最近 60 筆需求紀錄。對的，我的每一個對話記錄，都命令 memory ，要額外要求紀錄起來到單獨的檔案。

步驟二：對這 60 筆做模式分析： - A. 重複性需求：同類型需求出現 ≥ 2 次（同一 tag 反覆出現、同一 skill 被改 ≥ 2 次標為「反覆調整」） - B. 手動補償需求：摘要中含「手動」「批次」「補填」「修正」「指定」——代表這事 skill 該自己做卻沒做 - C. 跨 skill 串接缺口：同一天多個 skill 紀錄、後者依賴前者輸出，但要使用者手動銜接

步驟三：對每個發現的模式，產出具體的 skill 改進建議（要改哪個 SKILL.md 的哪一段、加什麼條件）。

步驟四：我看完建議，挑要做的，叫 Claude 直接動手改 skill。

這就是 skill 的健身教練——它監督你的 skill 有沒有變懶、有沒有漏洞、有沒有彼此打架。我每 2–3 週跑一次，每次都會找出 3–5 個可以優化的點。

對比一下：

沒有 /skill-review 有 /skill-review
Skill 寫完就忘 Skill 持續被體檢
同樣的事手動做了 5 次也沒發現 第 2 次出現就被標記
skill 之間銜接需要你親自串 發現串接缺口自動建議補一個 hook

這就是 S5 講過的「Skill 會長大」的真正機制——不是 Claude 自動讓它長大，是你寫一個 skill 去 review 其他 skill。第二階。

自我檢核

  • ☐ 我的 專案資料庫 第一週要先寫自己的話，不是貼別人的內容。AI 是來幫你連結你的想法，不是來餵你別人的想法的。
  • ☐ 每篇 note 標題用「完整句子」勝過「單詞」。例：「Agentic AI 跟對話式 AI 的差別」 > 「Agentic AI」。理由：完整句子當 wikilink 出現時可讀性高 10 倍。

S8 ｜ 訓練技巧：用 Supervised Learning 把 Skill 教得更好（16:10, 15 min）

一句話

「監督式訓練」對 skill 來說 = 你糾正它一次 → 把糾正寫進 SKILL.md 或 memory → 下次自動對。

跟 ML 的 supervised learning 同名同精神，但不用算梯度——你就是 loss function，SKILL.md 就是 weights。

三層記憶（從窄到寬）

當 Claude 做錯了，糾正寫進哪一層？

層 寫在哪 何時用
單一 skill .claude/skills/<name>/SKILL.md 只跟這個 skill 有關的規則
整個專案 <project>/CLAUDE.md 這個資料夾下所有對話都該遵守
跨對話記憶 ~/.claude/memory/ 關於你這個人的偏好、不限專案

Loop 長這樣

1. 你打 /skill
2. Skill 跑，出 90% 對的東西
3. 你看出哪 10% 不對 → 講出「應該是 X 不是 Y」
4. Claude 修正當下的結果
5. **關鍵：你接著說「把這個規則記下來，下次自動套用」**
6. Claude 改 SKILL.md（或 CLAUDE.md / memory）
7. 下次跑 /skill → 自動 100% 對

第 5 步是大家最容易漏的——光糾正一次，下次它還會犯。必須明說「記下來」。

我的兩個訓練做法

抽象的監督式循環我講完了。再講兩個我自己天天在做的具體做法，給大家拷貝。

做法 1：CBS 個案法（學得獎作品 → 練陌生題 → 比對差異 → 記錄）

我教研究所的 CBS 個案分析時，自己也用同一套循環訓練 Claude：

  1. 學得獎作品：把過去得獎的個案解答整批丟給 Claude 讀，叫它自己歸納「為什麼這份得獎」——是論點清楚？是資料引用方式？是結論收得乾淨？
  2. 練陌生題：給它一個沒看過的新個案，叫它先寫一份解答。不要先給標準答案。
  3. 比對差異：拿出真實的得獎答案，叫它「對照你剛剛寫的，差在哪」。它會自己列出 5–10 條差異。
  4. 記錄：把這些差異寫進 skill——下次寫新個案，自動帶入這些判準。

幾輪下來，它寫個案的水準從「資料筆記」變「能投獎的論證」。重點不在它一次寫多好，在於把每次差異都沉澱回 skill 裡。

做法 2：/learn-style ——對照真實版本萃取風格

這是我自己寫的一個 skill，專門解一個問題：Claude 寫的東西「對但不像我」。

流程：

  1. 我跟 Claude 各寫一篇同主題的短文
  2. 把兩份貼進 /learn-style
  3. 它逐句對照：「你開場是『提到大野城多數人會想到 X』，他開場是『大宰府的玄武，現在稱為四王寺山的山頂上』——你的開場是雜誌 hook，他的是空間方位事實」
  4. 把觀察到的差異寫成「風格條目」，存進 memory/richy_style.md
  5. 下次寫同類短文，這條規則自動套用
  6. 但目前為止我沒有真的這樣用過，只是訓練測試

現在 richy_style.md 累積了 68 條規則——從「動詞要口語帶台味」到「結尾不要寫『家的味道』『療癒了疲憊的旅人』」都涵蓋。

從 /learn-style 萃取的 10 條：AI 預設風格 vs. 我的風格

把這一年的對照結果整理成表。左欄是 AI 不被糾正時的預設語氣，右欄是我的真實寫法：

# 場景 AI 預設風格 ❌ 我的風格 ✅
1 開場 hook 「提到大野城，多數人會想到 ……」 「大宰府的玄武，現在稱為四王寺山的山頂上，有一座 1300 年歷史的古城。」
2 動詞 「全軍覆沒」「亡命」「席捲」 「打爆」「逃命」「挺好爬的」
3 抒情收尾 「靜靜訴說著歷史的見證」「療癒了疲憊的旅人」 「每個都道府縣都有自己的菜單，福岡就有燒鳥便當，算是有顧及在地特色。」
4 標點 「透明度設計訊號——例如外部認證——的效果」（破折號插入） 「透明度設計訊號，例如外部認證等，的效果」
5 負面體驗 「口味偏鹹、略重口」 「真的是鹹到頭痛、腎痛的那種」
6 食評體驗單位 「適合與家人朋友共度美好時光」 「小犬很聰明，一口都沒吃，我是越吃越難過」
7 政策跨境衝擊 「歐盟法規具備域外效力，市場地原則適用」 「歐洲的鐵拳也是會打過來的，先封鎖歐盟使用者」
8 AI 揭露義務 「應主動告知使用者其內容由 AI 生成」 「AI 都必須自我介紹」
9 監管者風格對比 「歐盟採嚴格強制取向，台灣傾向指導性原則」 「歐盟寫得這麼斬釘截鐵，事業主管機關還是很溫柔體貼的」
10 結尾 「我們應該共同關注，迎接 AI 時代的挑戰」 「台灣的公司，不管軟硬體，都要開始檢查一下：UI 寫了沒？合約補了沒？技術標記裝了沒？」

這些不是我教 Claude 的 prompt——是它從我親寫的版本自己萃取出來、存進 memory 的規則。下次叫它寫一篇歐盟法規評論，它出來的初稿就是右欄風格，不是左欄。

這就是 supervised learning 的真實樣子。沒有 GPU、沒有 dataset——只有「我寫一篇 + 它寫一篇 + 對照差異 + 記下來」這個循環，重複 100 次。

Case 2：寫 SNS 文章

第一次寫出來的文章：太長、太多術語、開頭不夠抓人。

糾正循環（連續 3–5 次）：

  • 第 1 次：「太長，限 280 字」→ 記
  • 第 2 次：「術語要白話換掉」→ 記
  • 第 3 次：「開頭要有反直覺事實」→ 記
  • 第 4 次：「結尾要留問題給讀者回覆」→ 記
  • 第 5 次：「禁用『#』hashtag，看起來像行銷」→ 記

5 次之後，/sns-draft 出來的東西已經像你的聲音了。

為什麼這比 fine-tuning 好

  • 零訓練成本：你不需要準備 dataset、不需要 GPU
  • 可解釋：規則用人話寫在 SKILL.md，你看得懂、改得動
  • 可移植：複製 SKILL.md 給同事，他立刻有同一套規則
  • 可回溯：規則不對就刪掉那一行，不像 fine-tune model 改不回來

高階：把「為什麼」也記下來

差的記法：

- 中文不要用破折號

好的記法：

- 中文寫作禁止破折號插入語
  - Why: 台灣中文書寫慣例不用，使用者反覆糾正過
  - How to apply: 改用「，例如 X 等，」或括號；論文與新聞稿一律適用

加上 Why + How to apply，邊角情況 (Edge-Case Condition) 模型能自己判斷該不該套用，不會死板。

自我檢核：你的 Skill「會長大」嗎

跑完 skill 後問自己：

  • ☐ 這次糾正的內容，寫進 SKILL.md 了嗎？沒寫 = 下次重犯
  • ☐ 規則有附 Why 嗎？沒附 = 邊角情況會被誤套
  • ☐ 規則放對層級了嗎？（單 skill / 專案 / 跨對話）
  • ☐ 一週後回頭看 SKILL.md，它比一週前長了嗎？沒長 = 你沒在訓練它
